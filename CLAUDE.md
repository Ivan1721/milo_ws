# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Workspace for **Milo** (`andesrobot`), a mobile manipulator: hoverboard differential base, RPLIDAR C1,
IMU, a vertical lift on a column, a 6-DOF arm and a two-finger gripper. ROS 2 **Humble**, Gazebo
**Classic 11**. Everything normally runs inside Docker (`docker/`, image `milo:humble`, container
`milo`); `ros2_ws/` is bind-mounted into the container as `/ros2_ws`, so code is edited on the host
and built/run in the container.

The user's own work is **the arm only** (`andesrobot_arm` + the arm parts of `andesrobot_description`).
Don't add or propose base-navigation features as next steps unless asked.

Repo docs are written in Spanish for students, with very dense explanatory comments (every launch,
xacro, yaml and script explains each concept). Match that: Spanish comments and log messages, same
comment density. `README.md` is step-by-step for non-experts; per-package details live in
`docs/*.md` (`andesrobot_description/docs/ROBOT.md`, `andesrobot_arm/docs/BRAZO.md`).

Repo-root `docs/` holds non-code material: `docs/informe/` (the technical report as Markdown,
`README.md` + `img/`, so GitHub renders it, math and mermaid blocks included; this is the live version: the claude.ai
artifact is a frozen 19-Oct-2026 copy with a banner pointing here, so don't sync it), `docs/navegacion/` (the navigation report, same style; figures in `img/` regenerated by `andesrobot_navigation/scripts/figuras_nav.py`) and `docs/hardware/` (vendor manuals, datasheets, CAD for the EB300 arm,
EBG-20 gripper, motors and Orbbec camera; third-party, so only its `README.md` index is versioned).
`docs/literatura/README.md` is the literature review (methods per pending task, with references;
open-access PDFs in the gitignored `docs/literatura/pdf/`) and `docs/tecnologias/README.md` the
technology review (tools per layer, closed-loop diagrams, NBV feasibility).
`docs/PENDIENTES.md` is the backlog of what is left on the arm, one short self-contained entry per
task (context, what to do, done-when, where to look): read it first and open only the files the
entry names, instead of the whole report. Update it when a task closes or a new one appears. The
project skill `.claude/skills/actualizar-informe` maps each kind of change to the docs it touches.
`docs/dependencias/README.md` compiles every software/driver/hardware dependency by stage (development
vs deployment) with the versions measured in the image; update it when the Dockerfile or hardware changes.
`docs/prueba_desde_cero.md` is the ordered test checklist from an empty PC to the gripper reaching
the door handle (`manija_node acercar:=true`), including the start pose in front of the handle.
Keep `ros2_ws/src/` for ROS packages only.

## Commands

All from `~/milo_ws` on the host:

```bash
./sim.sh                 # mapping sim: Gazebo + Milo (arm locked) + safety filter + slam_toolbox + RViz
./sim.sh brazo           # arm sim: Gazebo + Milo with arm/lift/gripper controlled + IK + RViz marker
./sim.sh casa            # mapping sim in the RoboCup@Home house (robocup_casa.world)
./sim.sh nav <mapa> [arena]   # autonomous nav: Gazebo + AMCL + Nav2 + twist_mux + safety (nav mode) + RViz
./sim.sh ir <lugar>|--lista   # send Milo to a named location from maps/casa_lugares.yaml (ir_a)
./sim.sh tour [N]        # visit all named locations, CSV to ros2_ws/resultados/
./sim.sh teleop          # drive (keyboard -> /cmd_vel_teleop)
./sim.sh build           # colcon build --symlink-install inside the container
./sim.sh shell           # bash inside the container (ROS sourced)
./sim.sh stop            # docker compose down
./sim.sh imagen          # rebuild the Docker image; starting no longer does (only warns if docker/ changed)
./sim.sh mapa [nombre]   # save the slam map
./sim.sh cpu|software|sin-gazebo|gpu   # no NVIDIA / CPU rendering (black windows) / no gzclient / GPU check
./robot.sh ...           # same commands on the real robot's laptop (USB lidar + hoverboard);
                         # extra: rviz, puertos, camara; ports via LIDAR=/dev/ttyUSB0 HOVER=... ./robot.sh
./robot.sh camara [alineada:=true] [rviz:=true]   # real gripper camera alone (no lidar/wheels needed)
```

Docker plumbing shared by both scripts lives in `docker/lib.sh` (`milo_init`, `milo_up`, ...).
External drivers (today `sllidar_ros2`) are pinned in `docker/milo.repos` and fetched at image build
time with `vcs import` into `/opt/milo_drivers` (outside the workspace). To add or bump one, edit that
file; it lives in `docker/` because that is the image build context. Exception: the camera driver is
pinned in `docker/camara.repos` and built in a layer after YOLO, so bumping it doesn't reinstall
PyTorch; it is patched at build time (`docker/parches/`). Own drivers (hoverboard) stay
in `ros2_ws/src/drivers/`. Versions: the base image is pinned by digest and every pip package by
`docker/requisitos_vision.txt` (`pip -c`, CLIP by commit in the Dockerfile); apt packages are not.
`milo_up` uses `up -d` without `--build`, and the container sets `YOLO_AUTOINSTALL=false`.

`build`, `shell` and `teleop` need the container already up (started by `./sim.sh` or
`./sim.sh brazo` in another terminal). `--symlink-install`: edits to existing `.py`/`.xacro`/`.yaml`
take effect on relaunch; new files need `./sim.sh build`. `milo_up` builds automatically if
`install/` doesn't exist yet or a package from `colcon list` isn't installed.

Tests (pytest, no ROS graph needed; run inside the container after a build):

```bash
./sim.sh shell
source /ros2_ws/install/setup.bash
cd /ros2_ws/src/andesrobot_arm && python3 -m pytest -q test                      # all
cd /ros2_ws/src/andesrobot_arm && python3 -m pytest -q test -k ik_con_lift       # one test
cd /ros2_ws/src/andesrobot_safety && python3 -m pytest -q test
```

Gazebo smoke test, headless (~2 min, container up, no other sim running):
`bash /ros2_ws/src/andesrobot_arm/scripts/prueba_gazebo.sh` (controllers, joint_states, camera rates,
a reachable pose via TF, with MoveIt also: table in the scene, a pose inside the table rejected,
OctoMap filled; gripper open/close, clean shutdown). `MOVEIT=false` runs it with `arm_ik_node`.

There are no ament_lint tests; keep Python within 99 columns (flake8) to match the code.

CI (`.github/workflows/ci.yml`, GitHub Actions on every push to `brazo`/`main` and every PR) runs
three jobs without ROS or Docker: `pytest` of `andesrobot_safety` plus the arm tests that need no
ROS (`test_torques.py`, `test_medidas.py`, `test_revisar_docs.py`, `test_moveit_opciones.py`, `test_manija.py`, `test_agarre.py`), `flake8 --max-line-length=99`
on `andesrobot_arm`, `andesrobot_description` and `andesrobot_moveit_config`, and
`scripts/revisar_docs.py` (broken links/anchors across every `.md`, informe figures and sections in
order, `\operatorname` forbidden because GitHub rejects it, and every "**N de N** en `X`" test count
in the docs must match the tests in the code). `test_kinematics.py` (needs ROS) and the Gazebo smoke
test stay manual inside the container; when you add or remove tests, update the counts in the report.

**Never run `colcon build` natively inside `~/milo_ws/ros2_ws`.** The container reuses
`ros2_ws/install/`, and host-built paths break it. For native (non-Docker) runs, build elsewhere:
`colcon build --symlink-install --build-base /tmp/milo_build --install-base /tmp/milo_install`
and `source /tmp/milo_install/setup.bash`. Natively, VS Code terminals auto-activate Anaconda
(`(base)` prompt) and ROS Python fails with `No module named 'rclpy._rclpy_pybind11'`:
`conda deactivate` first.

## Architecture

Packages (`ros2_ws/src/`):

| Package | Role |
|---|---|
| `andesrobot_description` | URDF/xacro, meshes, `rsp.launch.py`, `display.launch.py`. Single source of truth for geometry. |
| `andesrobot_gazebo` | `sim.launch.py` (world + rsp + spawn, arm **locked**), `andesrobot_arena.world`, `robocup_casa.world` (generated by `tools/gen_casa_robocup.py`, house centered at world origin, spawn = `CASA_SPAWN` in `sim.sh`; edit the script, not the .world) |
| `andesrobot_bringup` | top-level launches: `sim_mapping` (what `./sim.sh` runs), `robot`/`robot_mapping` (real), `rviz_mapping`; `milo_controllers.yaml` (diff drive, real robot) |
| `andesrobot_safety` | `safety_filter`: `/cmd_vel_teleop` + `/scan` → stops before obstacles → `cmd_vel_out`. Math in `logic.py` (unit-tested), ROS in `safety_filter.py` |
| `andesrobot_slam` | `laser_filters` (removes the column from the scan) + slam_toolbox online async |
| `andesrobot_navigation` | Nav2 for Milo: `navigation.launch.py` (map_server + AMCL + Nav2 nodes by hand + twist_mux), `nav2_params.yaml` (DWB, off-center footprint), `ir_a` (go to named locations / tour + CSV), `marcadores`. Bringup: `sim_navigation`, `robot_navigation` (real, untested) |
| `andesrobot_arm` | arm kinematics/IK, `arm_ik_node`, `arm_moveit_node`, `arm_marker_node`, `arm_controllers.yaml`, `arm_sim.launch.py` |
| `andesrobot_moveit_config` | MoveIt 2 config for the arm: `andesrobot.srdf`, `kinematics.yaml` (KDL), `joint_limits.yaml`, `moveit_controllers.yaml`, `ompl_planning.yaml`, `sensors_3d.yaml` (OctoMap). Config only; launched from `arm_sim.launch.py` |
| `drivers/hoverboard_hardware_interface` | C++ ros2_control hardware plugin for the real wheels (serial) |

**Sim vs real parity for the base:** same topics in both. Sim uses Gazebo plugins from
`andesrobot.sim.xacro` (`libgazebo_ros_diff_drive` publishes `/odom` + TF `odom→base_footprint`,
ray sensor → `/scan`, IMU, `libgazebo_ros_joint_state_publisher`). Real uses ros2_control
(`andesrobot.ros2_control.xacro`, only with `use_hardware:=true`) + `diff_drive_controller`; the
safety filter's output is remapped to `/diff_drive_controller/cmd_vel_unstamped` there.

**URDF switches** (`andesrobot.urdf.xacro` args, documented in `docs/ROBOT.md`): `lock_arm` (arm, lift,
fingers become `fixed`; used by the mapping sim because the unactuated arm would collapse),
`simple_collision` (primitive boxes on `base_link`, including a fixed "brazo" box; arm links then have
**no** collision), `sim_lidar`/`sim_imu`, `use_hardware`/`hoverboard_port`, `arm_control` +
`arm_controllers_file`, `gripper_camera`. Frames: `base_footprint` on the ground under the wheel axle;
`base_link` at the profile center (z = 0.08935, axle 6.8 mm below it); `laser` is the C1 optical frame.
Since 2026-11-08 the package is the structure team's **rev. 1** (repo
`AndesRobot-Oficial/Structure-Embedded-Systems_MILO`, folder `milo_description`, copied in as is:
V-slot frame, head with RealSense, electronics, real masses 36.8 kg, no ballast; arm bolted to the
carriage plate with no printed round base, so `joint_1` sits at `arm_base_link_1` and the arm is
30 mm lower than before; `lock_arm:=true` fixes the arm in a folded pose; `gripper_imu_link` on
`link_6_1`, no sensor). Arm meshes and the arm_control/gripper_camera/sim xacros were identical.
All SRDF pairs were regenerated from scratch; the `cabeza_link`–`link_3_1` pair is `Default`
(they overlap at the zero pose Gazebo starts in), so MoveIt does not check arm vs head (P16).
After it the smoke test, `agarre_node tenedor` and `manija_node acercar:=true` passed with no pose changes. The CAD was modeled rotated 180° about Z, fixed
with `rpy="0 0 π"` at base-level joints/visuals; a new child of `base_link` likely needs the same.

**Arm in simulation** (`./sim.sh brazo` → `andesrobot_arm/launch/arm_sim.launch.py`):
- Processes the xacro itself with `lock_arm:=false arm_control:=true` instead of using
  `rsp.launch.py`, because `gazebo_ros2_control` (Humble) re-passes `robot_description` as a CLI
  `--param` and fails to parse it when the URDF has XML comments (the controller manager never
  starts). The launch strips comments; keep that if you change how the URDF is produced.
- `arm_control:=true` includes `andesrobot.arm_control.xacro` (`GazeboSystem`, **velocity** command
  interfaces for lift + joint_1..6 since 2026-11-07, **effort** for both fingers) and removes the arm joints from the
  Gazebo joint_state plugin so `joint_state_broadcaster` is their only publisher.
- Gripper by force since 2026-11-07 (P15 phase 1): `gripper_controller` (JTC, effort, P-only
  `gains` p=10000) holds **both** `right_finger_joint` and `left_finger_joint`; goals must send both,
  mirrored (`[q, -q]`, open 0.016, closed -0.007), single-finger goals are rejected. With
  `arm_control:=true` the URDF drops the left finger's `<mimic>` (SRDF `pinza` group and
  `moveit_controllers.yaml` list both): an effort mimic only copies the force, so the left finger
  drifted (stopped at -11 mm when opening). Force cap = finger `<limit effort>` = `gripper_force`
  20 N (Gazebo truncates SetForce to it; EBG-20 pinion pitch radius ≈ 7 mm from CAD part 015 → MG99x
  max ≈ 65 N/finger), `gripper_damping` 400 N·s/m with `implicitSpringDamper`, finger contact
  mu 1, kp 1e6, kd 300 (ODE's default rigid contact gave 3-6 mm jumps in 3/10 closes; minDepth /
  maxVel 0 didn't help; kp 1e5 let a held box creep down). `scripts/prueba_pinza.py` (sim running,
  best with `mesa:=false camara:=false`) closes on static boxes of 10-45 mm and checks the
  **opening** (within 0.1 mm); closing fully, both fingers sit at the force cap so nothing centers
  them and the pair sways sideways (reported, not checked). Test boxes must be shorter than the
  21 mm finger pad (a 20 mm box hit the pad edge and jittered).
- P15 phase 2 (2026-11-07): `scripts/prueba_levantar.py` puts a loose 30 mm box (p3d plugin →
  `/caja_suelta/odom`) on a static pedestal between the fingers, closes, raises the lift 5 cm,
  holds 10 s. With position-commanded arm joints the box rose 0 mm: gazebo_ros2_control 0.4.10
  teleports position joints (no velocity), so finger friction can't carry anything. Hence
  `arm_controller` is now **velocity** (JTC PID `p` 20, lift 60, `ff_velocity_scale` 1; lift
  sags 0.3 mm; smoke test green with and without MoveIt). Measured joint velocity at rest jitters
  up to ~0.05 rad/s, so `stopped_velocity_tolerance` is 0.1 (with 0.01 every trajectory ended in
  GOAL_TOLERANCE_VIOLATED although the arm arrived; the smoke test now also requires "Objetivo
  alcanzado" in the log). To grasp, command each finger 2 mm
  **inside** the object width (`--apriete`, 20 N with p=10000), not fully closed: that centers
  the object. 0.1-0.5 kg hold within 0.4 mm/10 s (8/8); 1 kg slips 2-3 mm. Marker/fork with convex
  collision still pending (no CoACD/V-HACD in the image).
- One `arm_controller` holds `vertical_lift_joint` + `joint_1..6` (so 7-DOF IK solutions move in
  sync; `allow_partial_joints_goal: true`); `gripper_controller` holds both fingers (above).
- Controllers are spawned only if `spawn_entity` exits 0.
- Data flow: `arm_marker_node` (interactive marker at `gripper_tcp`) publishes `PoseStamped` on
  `/arm_target_pose`. With `moveit:=true` (default since 2026-10-18) `arm_moveit_node` turns it into
  a `MoveGroup` action goal (`/move_action`, group `brazo` = `base_footprint → gripper_tcp`, 7
  joints) and `move_group` plans a collision-free path (OMPL RRT-Connect, KDL IK, TOTG timing) and
  executes it on `/arm_controller/follow_joint_trajectory`; failures are logged in Spanish with the
  MoveIt error code (`MOTIVOS` in `arm_moveit_node.py`). With `moveit:=false` the old `arm_ik_node`
  does the IK itself (no collision checking; params `use_lift`, `position_only`, `lift_weight`).
- MoveIt details: `move_group` is started by `OnProcessExit` of the controller spawner (so the
  FollowJointTrajectory servers exist); `MoveItConfigsBuilder('andesrobot',
  package_name='andesrobot_moveit_config')` processes the **same xacro with the same mappings** as
  `robot_state_publisher`. The planning scene only knows robot frames (`Unknown frame: odom`), so
  the test table (two boxes published by `arm_moveit_node` on `/planning_scene`) and the OctoMap
  (`octomap_frame`) use `base_footprint`; fine while the base doesn't move. `octomap:=false`
  disables `sensors_3d.yaml`. Untested options (defaults unchanged, logic in `moveit_opciones.py`): `ik:=pick_ik`
  (`config/kinematics_pick_ik.yaml`; TRAC-IK has no Humble package, pick_ik is in the Dockerfile) and
  `suavizado:=ruckig` (adds `AddRuckigTrajectorySmoothing` before TOTG in the OMPL adapters). Objects seen by the camera become obstacles, so a pose touching them
  is rejected. Regenerate the SRDF `<disable_collisions>` pairs after geometry changes with
  `ros2 run moveit_setup_assistant collisions_updater` (command in `docs/BRAZO.md`); the SRDF keeps
  its hand-written header, so merge the generated pairs instead of overwriting the file. RViz uses
  `rviz/arm_moveit.rviz` (PlanningScene + Trajectory displays) and needs the robot_description
  params. The image installs `ros-humble-moveit`, `moveit-ros-perception` (OctoMap updater, not in
  the metapackage) and `moveit-setup-assistant`.
- Uses mesh collisions by default (`simple_collision:=false`) because the simple boxes leave the arm
  without collision.
- `gripper_camera:=true` (on by default in `arm_sim`, arg `camara`) adds the Orbbec Gemini Plus
  behind the wrist since 2026-11-07 (`andesrobot.gripper_camera.xacro`, mesh `orbbec_gemini_plus.stl`):
  an estimated L bracket on the rear cap of the joint_6 housing (`link_5_1`, x = +0.056), hinge
  raised 3 cm above it (lower, the gripper body hid half the image), 20° tilt; it sits 16 cm behind
  and 10 cm above the TCP, the gripper fills the bottom third of the image, and it does NOT roll
  with joint_6, so `arm_moveit_node` adds a goal JointConstraint |joint_6| <= `joint_6_max` (π/2)
  or MoveIt may pick joint_6 ≈ π and the image comes out upside down (`arm_ik_node` has no such
  guard). Start poses in `docs/prueba_desde_cero.md` and `evaluar_objetos.VISTAS` were recomputed
  for it. Regenerate SRDF pairs if the mount moves again. Gazebo
  color, depth (+points) and IR sensors publishing `/gripper_camera/{color,depth,ir}/image_raw`,
  `/gripper_camera/depth/points`, same names as the real `OrbbecSDK_ROS2` driver. Plugin topics are
  renamed with `<remapping>`. `ros2 run andesrobot_arm capturar_camara` saves one image per channel to
  `ros2_ws/capturas/` (gitignored). `arm_sim` also spawns `worlds/mesa_prueba.sdf` (arg `mesa`); its
  objects are links of one model, so it needs `<self_collide>true` or they fall through the table;
  the table link is fixed to `world`. `puerta:=true` spawns `worlds/puerta_prueba.sdf` instead of the
  table (door-opening challenge, push only): leaf at x = 0.80 opening away from Milo, lever handle
  at (0.75, −0.38, 1.0), springs on hinge and handle (Gazebo Classic `<spring_stiffness>` works;
  verified), ground-truth angles on `/puerta/joint_states`, no latch yet. `ros2 service call
  /apply_joint_effort` did not move it in tests; `gz joint -m puerta_prueba -j bisagra -f N` does.
- Vision: the image has Ultralytics (YOLOv8/11/YOLOE) + PyTorch CUDA + Ultralytics' CLIP, installed
  with pip in a precise order (see the Dockerfile comment: `numpy<2` for ROS, Ubuntu's pip for
  ultralytics because the new pip refuses to replace apt's sympy, new pip only for CLIP, then
  apt's `python3-setuptools` reinstalled because colcon breaks with setuptools >= 80). Weights go
  to `ros2_ws/modelos/` (gitignored). Pretrained YOLOE / YOLOv8-OIV7 localize the simulated handle
  but misclassify it (conf < 0.06), so `scripts/generar_dataset_manija.py` auto-labels images
  (box, polygon, 3 keypoints eje/agarre/punta) from the known door geometry + TF into
  `ros2_ws/datasets/manija_sim/{train,val}` (gitignored); goals go in `base_footprint` (MoveIt has
  no `odom`). `--variar K` respawns a randomized door every K images (`sdf_variante` edits
  `puerta_prueba.sdf` with ElementTree: materials, lever size, a dim point light, spring
  references for hinge/handle angles; unique model names; first batch is always the original;
  brighter lights wash the image out). The base slips ~1 mm per arm move even in free air
  (cause measured in `scripts/deriva_base/`: the wheels roll, not slide, because ODE's quick
  solver at the default 50 iterations doesn't hold the diff-drive's zero-velocity motor under
  the arm's load; `<iters>200</iters>` in the `<physics>` of both worlds, applied 2026-11-05, mostly removes it
  (with velocity control, 2026-11-07: 1 cm / 0.8° after ~30 arm moves; not re-measured); real-time
  factor of the full arm sim and base driving not re-measured yet): a 300-image run drifted 0.41 m/24°
  and MoveIt then failed 1/3 of views. The generator therefore sets `acceleration_scaling` 0.2 on
  `arm_moveit_node` at runtime, skips views with the TCP < 12 cm from the leaf, and stops at 15 cm
  drift (relaunch the sim, continue with `--inicio`). `scripts/entrenar_manija.py --tarea pose|seg|det` hard-links
  the split into Ultralytics' images/labels layout and fine-tunes yolov8s-* into
  `ros2_ws/modelos/entrenamientos/`.
- Objects: catalog `config/objetos.yaml` (26 scanned objects, 23 classes; no model for
  colgate_box, key, redbull_can, drink), logic in `catalogo_objetos.py` (tested).
  `objetos:=true` (original cup + bowl) or `objetos:=taza,platano,...` (ids or classes, up to 10
  in rows at x 0.80/0.95) spawns `worlds/mesa_objetos.sdf` (same table as `mesa_prueba`, so
  MoveIt's table matches) and, after the controller spawner exits (spawning many textured meshes
  at once made it time out), each object via `spawn_entity -database` from
  `ros2_ws/modelos/gazebo/` (gitignored, ~370 MB; the launch appends it to `GAZEBO_MODEL_PATH`).
  `scripts/descargar_objetos.py` fetches Fuel (GSO) zips and YCB google_16k/berkeley meshes
  (builds their SDF) and fixes each one, every fix found by testing: texture next to the mesh,
  `Ka` white, `usemtl` added (else black/gray), catalog mass + box inertia, collision = mesh
  bounding box (mesh collision + real mass made the cup tip over), bbox in `milo.json` (YCB
  origins aren't at the base). `.glb` (Fuel water bottle) and the classic Coke can (fell through
  the table) were dropped. `objeto_node` (geometry in `objetos.py`, tested) uses the team's
  27-class YOLO11n detection model `ros2_ws/modelos/objetos/best.pt` (gitignored, copied by
  hand): median of 25 depth rays from the box center → 3D point, then the same two-step
  `manija.Acercamiento` (0.30 m, then `distancia_final` 0.10 m). It also publishes grasp
  measurements from a 15x15 ray grid over the whole box (`agarre.analizar_objeto`: table = most
  populated height, object = > 4 mm above, PCA long axis, occupancy-histogram extent → length,
  width, center; not median/percentiles, which bias toward the denser near side):
  `/objeto/pose` (center + yaw of the long axis) and `/objeto/medidas` (Vector3: largo, ancho,
  alto).
- `agarre_node` (`ros2 run andesrobot_arm agarre_node tenedor`; id or class from the catalog;
  logic in `agarre.py`, `test/test_agarre.py`; launch with `objetos:=tenedor octomap:=false`):
  starts `objeto_node` (clase, confianza 0.2) if nobody publishes `/objeto/pose` and stops it on
  exit (SIGTERM handled), tries `vistas` (TCP xyz + aim point xyz; they aim 6 cm *before* the
  object at (0.80, 0) because the camera looks over the gripper, which otherwise hides it), waits
  for 3 stable measurements, rejects width > 45 mm, then MoveGroup to 10 cm above (gripper down,
  fingers across the long axis, `arm_moveit_node.meta_de_pose` shared), Cartesian descent
  (`/compute_cartesian_path` + `/execute_trajectory`, 10 % speed) to TCP = table + 20.4 mm (finger
  tips stick out 20.4 mm past the TCP along −X; MoveIt refuses lower) + 5 mm, fingers to width −
  2 mm each, checks they stalled (`hay_objeto`), attaches a box to `gripper_tcp` in the planning
  scene, lifts 10 cm (Cartesian, no collision check) and moves to `retraer`. If the TCP starts
  low (failed earlier run) it first rises 10 cm and goes to `retraer`: a free MoveIt path from
  near the table swept the (unmodeled) fork into the air. `hay_objeto` also rejects fingers still
  fully open (49 mm), which once counted as a grasp. Fork 3/3 on
  2026-11-07 (center within 1 cm, fingers stop at 27.1 mm, held ≤ 8° tilt); the cup is found and
  rejected (81 mm). Of the objects that fit, the model only recognizes the fork in sim (P14).

**Arm kinematics** (`andesrobot_arm/kinematics.py`, pure numpy, details in `docs/BRAZO.md`):
`ArmKinematics` walks the processed URDF from tip to base, so it always follows the xacro (no DH
table). Chains: `arm_base_link_1 → gripper_tcp` (6-DOF) or `base_footprint → gripper_tcp` (7-DOF
with the lift, `base=LIFT_BASE`). `from_xacro()` reads the **installed** `andesrobot_description`
xacro with `lock_arm:=false` (with the arm locked every arm joint is `fixed`). IK is weighted damped
least squares with random restarts within URDF limits; `arm_ik_node` gives the lift weight 10 so
it prefers arm joints. Full-turn revolute ranges (the provisional ±π) wrap instead of clipping.
The wrist isn't spherical (joint_4 ∥ joint_6), so there's no closed-form IK.

`gripper_tcp` (0.102 m along −X of `link_6_1`, between the finger pads) is the IK tip and the
marker's frame. `andesrobot_arm/scripts/figuras.py` regenerates `docs/figuras/` (renders, dimension
drawings, workspace and `medidas.json`) from the URDF + STL meshes; rerun it after geometry changes. `scripts/fig_articulaciones.py` (imports figuras.py, so needs the container) draws the
report's notation figure A (joint_2 and the lift over translucent URDF meshes, with every formula
symbol) into `docs/figuras/`. `scripts/fig_lazo_cerrado.py` (matplotlib only) draws the
report's figure B, the arm's closed-loop block diagram; `fig_lazo_moveit.py` reuses its helpers for
figure C (the same loop with MoveIt 2, what runs with `moveit:=true`). `fig_actualizacion.py` draws the two
update figures for team messages (camera-to-motors flow colored by already-there/new/pending, and a
before/after table); edit its `FILAS`/`PENDIENTES` when the state changes. The Markdown report links

directly; `docs/informe/img/` keeps only images that exist nowhere else (camera captures, range
plot, and figures 8/9: handle labels and model predictions, copied from the gitignored
`ros2_ws/capturas/` and the training run). The frozen claude.ai artifact has its own uploaded copies. `andesrobot_arm/torques.py` (pure numpy, tested in `test/test_torques.py`) and `scripts/calcular_torques.py` compute the static gravity torque per joint from the URDF masses (`--pesaje` prints the table of parts to weigh); a new module needs `./sim.sh build`. `andesrobot_arm/medidas.py` and `scripts/comparar_medidas.py` compare measured distances/stops with the URDF and the official DH and print the xacro lines (sheet: `docs/medicion_brazo.md`). Arm limits are **provisional** (`arm_lower/arm_upper/arm_effort/arm_velocity`
properties: ±π, 20 N·m, 1 rad/s; per-joint stops are `joint_N_lower/upper`, defaulting to arm_lower/upper); don't use them for real hardware.

Known sim behaviors: the own IK (`moveit:=false`) has no collision checking. `arm_controller` has goal tolerances
(`arm_controllers.yaml`: 0.02 rad, lift 5 mm, `goal_time` 1 s, path tolerance off) so a move whose
joints don't arrive aborts with GOAL_TOLERANCE_VIOLATED and `arm_ik_node` logs it, but **Gazebo
almost never blocked the arm**: position-commanded joints were rigid, so a collision with the table
or column tilted/pushed the whole base (measured 2026-10-17: TCP sent 2 cm into the tabletop
"arrives", base tilts 3° and slides 3.5 cm back) and the controller reported success. Not
re-measured with velocity control (Gazebo also imposes velocity with no force limit). Don't present the
tolerances as collision detection; the real protection is MoveIt's planning-scene collision
checking (default) or effort control with PIDs. `gripper_controller` has no tolerances on purpose (fingers stall on a grasped
object). The test table in `worlds/mesa_prueba.sdf` is anchored to `world` with a fixed joint so
the arm can't slide it. With the provisional ±π limits a joint can't cross ±π, so a
target "on the other side" makes a near-full turn (measured: 6.08 rad / 12.2 s for a 0.2 rad change).
A Ctrl+C can leave an orphan `gzserver` holding port 11345 (next launch dies with exit 255):
`killall gzserver gzclient` or `./sim.sh stop`.

**Navigation velocity chain:** controller → `/nav/cmd_vel_raw` → velocity_smoother → `/nav/cmd_vel`
(behavior_server also publishes there) → `twist_mux` (teleop `/cmd_vel_teleop` priority 100 > nav 10)
→ `/safety/cmd_vel_in` → `safety_filter` with `safety_nav.yaml` (`cmd_timeout` 0.5,
`turn_check_only_in_place`) → `/cmd_vel`. In sim the diff-drive plugin's odometry comes from the
world pose, so the SLAM `map` frame ≈ Gazebo world; `sim.sh nav` passes `CASA_SPAWN` to both the
spawn and AMCL's initial pose. Named locations are user-recorded (tf2_echo) in
`andesrobot_slam/maps/casa_lugares.yaml` (flat `name: {x, y, yaw}`); `nav_sobre_slam.launch.py` runs
Nav2 on top of live SLAM, publishing straight to `/cmd_vel_teleop` (practice only, no mux).

## Conventions worth keeping

- `sim.sh`/`robot.sh` print their header comment as help with `sed -n '2,Np'`: when adding an option,
  add its help line and update both the range and the comment that mentions it.
- Saving from RViz (File > Save) rewrites the `.rviz` file and deletes its comments.
- Robot docs use REP-103/105 (+X forward, +Y left, +Z up).
